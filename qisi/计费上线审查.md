# qisi API 计费上线审查

审查日期：2026-10-02。本文记录代码审查结论和待实施方案；**未修改任务提交、轮询、退款或数据库实现，以下风险尚未解决。**

## 本次上线边界

可以先部署真实的零余额注册、登录和管理后台；这不等于开放收费生成。收费渠道必须在服务端保持禁用，支付商户尚未接通时不能接受在线充值，也不能显示支付已开通。不要把“新用户余额为零”当作生成开关：管理员手动充值、已有余额、订阅或免费模型配置都会改变这个条件。

注册功能已经有真实用户落库和密码校验，不需要另造账号系统。本次新增了可配置的注册密码最小长度，并保持历史账号登录兼容；部署时仍需开启运行选项。建议本阶段配置：

```text
RegisterEnabled=true
PasswordRegisterEnabled=true
PasswordLoginEnabled=true
QuotaForNewUser=0
QuotaForInviter=0
QuotaForInvitee=0
EmailVerificationEnabled=false  # 仅在尚无可用 SMTP 时；不要假装能发送验证码

REGISTRATION_PASSWORD_MIN_LENGTH=15
GENERATE_DEFAULT_TOKEN=false
PUBLIC_BASE_PATH=/api-service
SESSION_COOKIE_SECURE=true
SESSION_COOKIE_TRUSTED_URL=https://cheeser.link
```

同时关闭签到赠送、免费额度和未准备的订阅销售入口；核对实际选项而不是只核对部署文件。`TRUSTED_PROXIES` 必须匹配真实反向代理链。生产会话密钥须独立、持久保存；管理员使用新的强密码，不能沿用曾在聊天中展示过的密码。启用现有认证限流，实际测试子路径、Cookie、登录和退出。无 SMTP 时网页已提供“无法邮件找回”的真实提示；不要把未经验证的邮箱当作恢复凭据。

主要证据：

- `controller/user.go` 的 `Register` 明确构造普通用户、忽略客户端注入的角色和余额，仅在验证开启时绑定邮箱；`model/user.go` 的 `Insert` 决定新用户额度。
- `common/account_password.go` 的 `InitRegistrationPasswordSettings` 支持 8–128 字符的注册下限配置；`controller/user.go` 在服务端执行，前端从 `controller/misc.go` 的状态字段读取同一规则。
- `router/api-router.go` 的注册和登录路由已有 `CriticalRateLimit` 和匿名请求体限制。上线还需验证反向代理下识别出的客户端 IP，而非仅确认代码中存在限流。
- `qisi/bootstrap-local.py` 在本次审查时仍写入 `RegisterEnabled=false`；生产配置不能直接照搬这个本地初始化选项。`qisi/start-local.py` 的本地非 Secure Cookie 设置也不能用于公网。

以上不是完整的 OWASP ASVS 合规声明。当前用户名重复提示仍可用于枚举，恢复机制的完整运营流程也未在本次建立；15 字符注册下限不等于已审计全部修改密码、恢复、MFA 和第三方登录路径。

## 已确认的收费风险

| 情况 | 代码位置 | 当前后果 |
| --- | --- | --- |
| 上游已受理，但网络断开或返回体损坏 | `relay/relay_task.go` 的步骤 7–10，`relay/channel/task/jsplugin/adaptor.go:ParseResponse` | 已预扣后返回提交错误；普通 JSON 解析错误不像 SSE 路径那样设置 `NoRetry`，可能再次提交 |
| 上游成功响应后客户端断开 | `controller/relay.go:executeTaskSubmissionWith` 的 `after_submit`、`before_reserve`、`before_insert` 检查 | 即使已经拿到上游任务 ID，也可能被改成取消错误，尚未建任务记录，触发退款 |
| 上游成功但任务落库失败 | 同函数 `InsertWithContext(c.Request.Context())` 和 deferred `!durable` 退款 | 返回错误并退款，上游仍可能继续执行；本地没有可查询任务 |
| 查询返回 404/410 | `service/task_polling.go:updateVideoSingleTask` | 直接 `failTaskFromPoll`，再进入失败退款；不能证明上游未扣费 |
| 查询超时、鉴权失败、限流、5xx、未知结构 | `service/task_polling.go:recordPollFailure` | 达到 `TaskPollMaxFailures` 后转失败退款，查询不可用被当成生成失败 |
| 超过任务最大等待时间 | `service/task_polling.go:sweepTimedOutTasks` | `FAILURE` 后退款，即使上游仍在执行 |
| 渠道信息临时不可读 | `service/task_polling.go:updateVideoTasks` | 批量把任务标成失败，失去正常轮询；这条路径本身未执行标准退款，但同样不代表上游失败 |

`qisi/likeai.plugin.js:parseTaskResult` 对未知响应和“完成但没有媒体”返回 `UNKNOWN` 是合理的，但宿主会把它累计成查询失败，最终退款，因此只改插件不能解决风险。`parseSubmitResponse` 错误文字中的“不要重试”也不是宿主重试控制。

`RetryTimes=0` 只能减少同一请求内部的自动重试，**不能阻止误退款，不能阻止用户/SDK 重复 POST，也不能解决返回前断线后丢失任务 ID**。

官方 LikeAI 文档在创建任务时预扣、成功结算、失败/取消退款；本次查看的创建参数未提供可依赖的幂等键或“按我方请求 ID 查询任务”契约。不能自行假定 `uid` 或任意请求头具有幂等作用。文档入口：<https://task.likeai.pro/api-doc>；公开正文：<https://task.likeai.pro/api/api-doc?doc_env=pro>。

## 建议的窄修复方案（未实施）

只针对可信的已锁定插件 `qisi-likeai` 生效；提交用宿主固定的插件身份，轮询用任务保存的插件/平台身份。不能让用户请求体或任意模型名称决定安全分支，也不改其他服务商的重试和退款语义。

1. **禁止自动重发创建任务。** 在 `controller/relay.go:decideTaskRetry` 对该插件明确返回停止，独立于管理员可改的全局重试次数。预校验、价格/余额不足、构造请求失败可以正常结束；一旦进入发出请求的阶段，不凭网络错误断言“没有受理”。

2. **调用上游之前保存待确认记录。** 最小插入点是 `relay/relay_task.go` 完成校验、构造请求和全额预扣之后，紧接 `DoRequest` 之前。使用现有 `tasks` 表，保存公开任务 ID、用户/令牌/渠道、预扣金额、计费快照、执行请求 ID；状态为现有 `UNKNOWN`，进度不写成完成，上游 ID 为空。写入失败时不发上游请求，并回退已经完成的本地预扣。不能等网络错误后才尝试第一次建记录。

3. **接管这条记录的退款边界。** `executeTaskSubmissionWith` 必须知道已进入“可能受理”阶段，不能继续沿用“没有最终成功落库就退钱”的 deferred 分支。网络错误、解析错误、客户端断开均保留预扣及待确认任务；给还能接收响应的客户端返回稳定的公开任务 ID 和明确的“受理状态待确认，请勿重新提交”。不要把未知伪装成成功或普通可重试的生成失败。

4. **成功响应补全同一条记录。** 获取上游 ID 后更新原记录，不能再新建一条。持久化使用有短截止时间、与客户端断开分离的上下文；客户端断开不应抹掉已知的上游任务。更新失败保留原待确认记录并告警。只在确认未发送、明确未受理，或确认上游终态失败/退款后释放预扣。非 2xx 不能一概当作未受理，例如网关 502 仍有歧义。

5. **未知任务不自动变成失败。** 在 `service/task_polling.go` 同时处理 404/410、查询失败阈值、超时清理和渠道不可读，均不得对 qisi 任务直接失败退款。已知上游 ID 可继续有节制地查询；超过自动处理期限转人工待核对。没有上游 ID 的待确认任务不发送查询。只有确认的上游终态才做结算/退款。

6. **排除错误查询及队列占满。** `model/task.go:GetUpstreamTaskID` 会把空上游 ID 回退为公开任务 ID；如果直接把待确认记录投入现有轮询，就会拿错 ID 去查询。必须在回退前跳过此类记录。`GetAllUnFinishSyncTasks`、`GetTimedOutUnfinishedTasks`、`HasUnfinishedSyncTasks` 也要配套处理待人工确认记录，避免它们反复占满前 N 条查询批次。可以复用 `UNKNOWN` 和现有字段，不必新增表或列，但筛选语义需要真实数据库验证。

7. **对账必须可操作。** 管理员需要能用公开任务 ID、请求时间、渠道、金额找到待核对项；未知金额应展示为“预扣待确认”。在核对上游实际账单/任务后，才能确定绑定上游任务、结算或退款。不能用一般“加余额”代替任务退款，否则任务状态和可退款金额仍不一致。第一版没有安全对账流程时，收费渠道继续关闭。

## 为什么上述改动仍不能直接宣称账务闭环

- **预扣与任务持久化不是一个事务。** 在“钱包/令牌已扣，记录未写”之间进程崩溃，仍可能留下孤立扣款。反过来先建记录，也必须区分是否真正扣款。若要求崩溃恢复，需要把 qisi 的预扣与意图记录纳入同一事务或可靠的持久化阶段；不能用一个内存布尔值解决。这里可以不加 schema，但仍然是数据库行为修改，本次未展开。
- **消费统计与退款有配对关系。** `service/task_billing.go:LogTaskConsumption` 累加用户/渠道用量；`RefundTaskQuota` 会减这些统计。如果待确认任务没有记录初始消费统计，却直接走标准退款，就可能得到负用量。需要记录一次且仅一次的预扣/统计阶段，不能简单“建 UNKNOWN 行然后跳过所有记账”。
- **退款本身有崩溃窗口。** `RefundTaskQuota` 先增加钱包余额，再清除 `task.Quota`；回写失败会告警。`service/funding_source.go:WalletFunding.Refund` 也明确说明余额增加不是幂等操作，不能盲目重试。终态 CAS 能减少正常并发重复退款，但不是跨进程崩溃的完整事务保障。
- **重复 POST 仍是另一问题。** 现有 `TaskID` 只是索引，不是唯一幂等约束，执行请求快照也不是去重凭据。禁用宿主重试不会合并用户重发。必须有可验证的稳定业务请求标识和唯一性保障，或取得上游正式幂等支持；不能把“最多尝试一次”写成“全链路只扣一次”。

因此建议先发布注册后台，暂停收费生成；不要为赶上线临时扩大通用账务修改，也不要把上述窄修复当成已完成的生产账务方案。

## 开放收费前的硬条件与验收

1. 持久化托管环境、HTTPS 和真实域名路由就绪，数据库/会话密钥不会随重启丢失；备份和恢复实际验证。
2. LikeAI 密钥只在服务器密钥配置中，模型白名单、时长/数量上限、费用表达式已经核对。20% 加价按当前真实成本计算，不能拿展示价格替代账户实际成本核对。
3. 上述不确定受理路径修复并验证；模拟上游先受理后断线、2xx 坏 JSON、客户端断开、结果写库失败：每次上游只收到一次创建请求、本地保留可追踪预扣任务，不自动退款或重发。预请求写入失败则上游收到零次调用。
4. 模拟查询 404、401、429、5xx、未知结构、超时以及渠道读取失败：全部保持可核对状态，不误退款；正常成功按真实用量结算，确定失败仅退款一次。并发轮询、重启和故障恢复覆盖余额、令牌、任务、日志的配对关系。
5. 覆盖客户端重发、响应丢失后找回任务与人工对账，保证操作流程不会诱导重复生成。已有正常供应商行为保留回归测试。
6. 数据库行为若按建议修改，按 `AGENTS.md` 在真实 SQLite、MySQL、PostgreSQL 上运行同一套测试，记录版本和结果。现有 `controller/relay_task_plugin_test.go` 已有 `TEST_TASK_DB_DIALECT`、`TEST_MYSQL_DSN`、`TEST_POSTGRES_DSN` 测试入口；优先扩展现有测试，不新建平行账务测试体系。只跑 SQLite、mock 或编译不满足此门槛。
7. 在线支付需要真实可用商户、回调验签、金额/币种校验、重复通知只入账一次、失败/退款处理完成。尚未开通渠道时只能明确提示未开放充值；后台手动储值需有真实订单/收款依据和审计记录。
8. 最后一次小额真实生成及账单对照要有明确付费测试预算授权。目前用户只批准了加价比例，未批准生成测试费用；本次未调用任何付费生成。

## 已完成验证与本次限制
